## QRVM facts the code must respect (verified in the client and compiler sources)

- `mload`, `mstore` and `calldataload` move 64 bytes; `mstore8` is unchanged; memory grows in 64-byte words with expansion cost `3w + w^2/512`. Free memory pointer at `0x80`, initial value `0x100`, scratch space `0x00` to `0x7f`.
- Assembly `keccak256(p, n)` returns the 256-bit digest right-aligned in the 512-bit word; high-level `keccak256()` returns a left-aligned `bytes32`. All digest handling lives in assembly. Merkle compression: `mstore(0x00, or(shl(256, left), right)); parent := keccak256(0x00, 64)`.
- `calldataload` past the end zero-pads, so the exact-length check runs before any query data is read.
- Yul is full solc-0.8.24 Yul with unchanged opcode names; `addmod` and `mulmod` are 512-bit in assembly; `unchecked`, `immutable`, libraries, calldata slicing, custom errors, `--via-ir` and `verbatim` are available. Inline assembly reads only literal-valued constants by identifier, so a member access such as `Lib.X` is rejected; array lengths and indices are `uint256`.
- ABI: every static type pads to 64 bytes; the selector stays 4 bytes; a dynamic `bytes` tail is a 64-byte length word plus data padded to 64; log topics are 64 bytes with `bytes32` and the event signature hash left-aligned.
- Precompiles are pre-warmed: a STATICCALL to `0x03`, `0x05` or `0x06` costs 100. Builtins `shake256(bytes) returns (bytes64)` and `mldsa87verify(bytes64, bytes, bytes, bytes) returns (bool)` exist. Modexp header fields are 32-byte lengths.
- Calldata costs 16 gas per non-zero byte and 4 per zero byte; the transaction base cost is 21,000; `qrl_estimateGas` caps at 50,000,000, so an estimate can exceed the block cap.
- The transaction pool rejects any transaction above 131,072 bytes (`txMaxSize = 4 * txSlotSize` in `core/txpool/legacypool/legacypool.go`, error `oversized data`) before it reaches a block. This is a client constant outside the consensus rules, with no command-line flag. `qrl_call` and `qrl_estimateGas` execute such payloads.
- `gqrl --dev` exists with `--dev.period`, `--dev.gaslimit`, chain id 1337, a funded unlocked developer account and a simulated beacon; the precompile stubs `0x01` to `0x06` are pre-allocated in its genesis; the transaction fee is capped at 1 quanta per transaction, so the scripts send with the estimate plus 20 percent; the data directory persists across restarts.
- Wide literals (48 to 64 bytes) are materialised with `CODECOPY` at optimizer runs 200 and inlined as `PUSH` at runs 1000000 (`docs/GAS-PRIMITIVES.md`), which is the whole difference between the two settings.

## Parameter sets

Every set in this table is a benchmark profile with experimental soundness. The
bit column is the ethSTARK conjecture and is not a production security claim.

| C1                  | 1          | 100     | 16        | 0          | 3             | 3                  | 116              |
| C2                  | 2          | 50      | 16        | 0          | 3             | 3                  | 116              |
| C3                  | 3          | 34      | 16        | 0          | 3             | 3                  | 118              |
| Sweeps (C3, n = 16) | 3          | 34      | 16        | 0          | 1, 2, 3, 4    | 0, 3, 5            | 118              |

Trace sizes: n = 10, 12, 16, 20. The plan's gas model (calldata about `16 * S`, compute about `130 * hashes + 2500 * Q * R + 3000 * Q + 15 * Q^2 + 60k`) predicted C3 at 1.1M (n = 10) to 3.4M (n = 20), C2 at 1.3M to 4.5M and C1 at 2.1M to 7.9M. Measured on the developer node at runs 200 (`qrl_estimateGas` of `verify`): C3 1.74M to 4.28M, C2 2.17M to 5.69M, C1 3.75M to 10.1M; the model underestimates by 26 to 84 percent (mean 49) because its compute term is a coarse budget and the fold chains alone are half of the execution. The sweep (n = 10 and 12, so the cells stay tracked) shows arity 8 with a final polynomial of 32 coefficients (`c3-a3-f5`) as the cheapest c3 shape and binary folding as the most expensive. `docs/GAS-REPORT.md` carries every cell and the extrapolation to n = 24 (c3 about 5.8M, c2 about 8.1M, c1 about 14.7M).

## Risks tracked

1. Plonky3 shape churn between `0.7.0-rc.1` and the final release: pinned version and lockfile; the calldata layout carries a version byte.
2. Transcript subtleties (three instance observations, end-of-digest sampling, chaining value, rejection sampling, `checkPow(0)` no-op, `log_arity` observed after `final_poly`, `sample_bits` consuming a full u64): byte-level logging and the M3 replay test came before any Merkle or FRI code, and every vector replays.
3. Keccak alignment and 64-byte `mstore` clobbering: all digest work in assembly; harness tests on known keccak vectors first.
4. `calldataload` zero padding: exact-length check first; offsets unit-tested against the Rust layout.
5. Code size and gas caps: measured at M6 and M7 with three flag sets; no split needed; four cells above the 8M target are documented.
6. Dev node and Kurtosis differ (chain id, signing path, gas limit source): `scripts/lib/rpc.js` and `scripts/lib/devAccount.js` abstract both; the historical Kurtosis gas gate passed, while the new source-provenance-bound protocol gate remains pending.
7. Offline toolchains: the first `cargo build` and `make gqrl` need network access.
8. Docker and Kurtosis state: the daemon must be started; enclaves are recreated (Kurtosis 1.20 cannot resume a stopped one); a separate image namespace avoids collisions with `qrl2-qns`.
9. Duplicate query indices at small n: representative and consistency rules covered by a forced-collision vector.
10. Licensing: Plonky3 is MIT/Apache-2.0 and the copied Fibonacci AIR keeps its notice; the repository is GPL-3.0.
11. QNS review timing: the snapshot commits duplicate the uncommitted alignment; rebase and drop them once the QIP branch is committed.
12. Transaction-pool size cap: proofs above about 123 KB cannot be submitted as one transaction on an unmodified client; measured through `qrl_call` and `qrl_estimateGas` until the L2 design settles the submission path.
13. Gas measurements agree across the developer node and Kurtosis release gate; each stored cell records the compiler and settings.
14. Poseidon2 parameter risk after ePrint 2026/1692: keep the protocol hash-agile and close the exact-instance review before selection; Rescue Prime is the conservative candidate under the same gate.
15. Zero-knowledge ambiguity: the current proof format is explicitly non-ZK and the first product track is scaling; `docs/SECURITY-STATUS.md` controls any later privacy claim.
16. Bridge statement mismatch: constructor and deployment checks prevent a 24-byte Fibonacci verifier from backing the 128-byte batch bridge.
17. Toolchain provenance drift: `npm run check:provenance` requires clean Hyperion and go-qrl source trees whose `HEAD` revisions match the configured binaries; the scheduled live gate stops before node startup when this fails.
